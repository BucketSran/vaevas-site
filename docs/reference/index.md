## 维护原则

1. **原件冻结**。原件字节不变，按来源 commit 或 SHA256 认身份。v4 r53 有封印文件；v1、v2、v3 和早期题包没有统一封印，用"来源 commit + 文件 SHA256"认定。
2. **问题进勘误表**。发现的问题记进对应版本页的勘误表，不改原件。
3. **修订进新版本号**。修订版用新的版本号，例如 `v4-r53-e1`，只收改动过的题。每题指回原件路径和原件 SHA256，并写明解决了哪几条勘误。
4. **撤回的结论不删**。被撤回的条目留在表里，状态标"已撤回"，写明撤回原因和推翻者。
5. **legacy EVAS 通过 ≠ Spectre 通过**。legacy EVAS 和当前 EVAS 同源，结果一致不代表正确。状态为"待 Spectre"的题，在 Spectre 跑完之前不下结论。

### 勘误表的格式

每个版本页都用同一张表：

| 编号 | 题号 | 问题 | 证据 | 状态 | 修订位置 |
| --- | --- | --- | --- | --- | --- |

- **编号**：`<版本前缀>-E<三位数>`，例如 `v4-E001`。前缀有 `v1`、`v2`、`v3`、`v4`、`early`。编号**永不复用**，撤回的条目也占着编号。
- **状态**只用以下五种：

| 状态 | 含义 |
| --- | --- |
| 已确认 | 有可复现的证据，且经过独立核验 |
| 待 Spectre | 只有 Spectre 才能裁决，Spectre 跑完前不下结论 |
| 已撤回 | 原结论被推翻，保留记录 |
| 归 EVAS 修 | 原件没错，问题在当前 EVAS，修 EVAS |
| 进行中 | 证据还不够，或还没判清楚该归哪边 |

## 怎么新增一条勘误

给维护者的步骤：

1. **固定原件身份**。写下题目所在的原件路径，以及来源 commit 或文件 SHA256。v4 先核对 `RELEASE_SEAL.json`；不在本仓库的版本（v2、v3）写明来源 commit。
2. **留证据**。证据放在本地 `runs/<日期主题>/` 下。勘误表"证据"一栏写证据的路径（相对 vaEVAS 根目录，用行内代码写）或仓库链接。证据要能复现：写明用的是哪个仿真器、哪个版本、哪套 checker。
3. **定状态**。按上面的五种状态选一个。需要 Spectre 才能裁决的，填"待 Spectre"，不要先下结论。只有 legacy EVAS 的结果，不算 Spectre 证据。
4. **取编号**。在该版本页勘误表最后一行的编号上加一，不要补空号，也不要复用撤回的编号。
5. **填行**。"问题"写清现象和影响，例如"会让缺陷模型通过""读到的行不同，判定就变"；"修订位置"没有就写"尚无"；说明较长时写"见表后说明"，把详情写进表后的说明列表，让表格保持可读。
6. 在该版本页第 4 节"修订版"里同步状态。本页的汇总计数在构建时自动更新；状态写错或编号重复，`./site.sh build` 会报错。
7. **改状态时不删旧内容**。结论被推翻，就把状态改为"已撤回"，在"问题"一栏写"**已撤回**：原说法……撤回原因……"，并写明推翻者。问题被修订版解决，就在"修订位置"填修订版本号和目录，状态保持原样。
8. **不改原件**。任何修复都放进新的修订版目录，原件只读。
